What exactly is Git?

My "aha!" moment
Picture this: I'm working on a website project, making changes left and right. Everything's going great until I decide to "improve" the navigation menu. Three hours later, I've broken everything and can't remember what I changed. I had to start over from scratch because I didn't have Git. That's when I realized I needed a better way to track my changes.

Git is basically a time machine for your code. Think of it like the "Track Changes" feature in Microsoft Word, but way more powerful. Every time you save a version of your project (called a "commit"), Git remembers exactly what changed, when it changed, and who changed it.

Here's the thing that took me a while to understand: Git doesn't just save your files - it saves the entire history of your project. So if you mess something up, you can go back to any previous version. It's like having infinite undo buttons.

  • website_actually_final.zip

  • One clean project folder

So much cleaner and more professional!

Getting Git on your computer

The installation process is actually pretty straightforward, though it felt intimidating at first. Here's what worked for me on different systems:

Windows

Go to git-scm.com and download the installer. I recommend sticking with the default settings unless you have a specific reason to change them. The installer will also give you Git Bash, which is a terminal that works well with Git.

Mac

If you're on Mac, try typing git in Terminal first - you might already have it! If not, the system will prompt you to install the Xcode Command Line Tools. Alternatively, if you use Homebrew, just run brew install git.

Linux

Most Linux distributions have Git in their package repositories. On Ubuntu or Debian, use sudo apt install git. On CentOS or Red Hat, try sudo yum install git.

After installation, verify it worked by opening your terminal and typing:

Terminal
git --version
Success looks like: You should see something like "git version 2.39.0" or similar. The exact version doesn't matter much - any recent version will work fine for learning.

Setting up and creating your first repository

Before you start using Git, you need to introduce yourself. This information gets attached to every change you make, so people know who did what:

Set your identity
git config --global user.name "Your Actual Name"
git config --global user.email "your.email@example.com"
Pro tip: Use the same email address you plan to use for GitHub, GitLab, or wherever you'll host your code. This ensures your contributions are properly credited to your account.

Now let's create your first repository. A repository (or "repo" for short) is just a project folder that Git is keeping track of:

Create your first project
mkdir my-learning-project
cd my-learning-project
git init
What just happened?
When you run git init, Git creates a hidden folder called .git inside your project. This folder contains all the magic - it's where Git stores the history of your project. You don't need to understand what's in there (I still don't fully understand it), but knowing it exists helps explain how Git works.

The day-to-day Git workflow

This is where Git clicked for me. Once I understood the basic workflow, everything else made sense. It's a simple three-step process:

The Git Workflow (This is important!)

1
Edit your files normally
2
Stage the changes
3
Commit with a message

Let's walk through this with a real example. First, create a simple text file:

Create a file
echo "Hello, this is my first Git project!" > README.md

Now let's see what Git thinks about this new file:

Check the status
git status

Git will tell you that README.md is "untracked" - meaning Git sees the file but isn't keeping track of changes to it yet. To start tracking it, use git add:

Stage the file
git add README.md

Now the file is "staged" - it's ready to be saved as part of your project's history. Let's save this snapshot:

Save the snapshot
git commit -m "Add README with project introduction"
About commit messages: The text after -m is your commit message. Make it descriptive! Future you (and your teammates) will thank you. Instead of "fixed stuff", write "Fix navigation menu not working on mobile devices".

Commands you'll use every day

After using Git for a while, I realized I use the same handful of commands 90% of the time:

git status
Shows you what's changed, what's staged, and what's not tracked. I run this constantly - it's like asking Git "what's going on right now?"
git add .
Stages all your changes at once. The dot means "everything in this folder". Super convenient for most cases.
git commit -m "your message"
Saves a snapshot of your staged changes with a descriptive message. Think of it as saving your game progress.
git log --oneline
Shows a compact history of your commits. Great for seeing what you've been working on.
git diff
Shows exactly what changed in your files. Helpful for reviewing your work before committing.

Fixing mistakes (we all make them!)

Learning from my mistakes
I remember the first time I accidentally committed a file with sensitive information (an API key - oops!). I panicked and thought I'd have to start over. Turns out Git has solutions for almost every mistake you can make. Here are the ones that have saved me multiple times.

Oops, I changed a file but want to undo it

If you've modified a file but haven't staged it yet, you can reset it back to the last committed version:

Undo file changes
git checkout -- filename.txt

I staged something by mistake

If you ran git add on a file but want to unstage it:

Unstage a file
git reset HEAD filename.txt

I committed something but want to undo it

This undoes your last commit but keeps your changes so you can fix them:

Undo last commit (safely)
git reset --soft HEAD~1
A word of caution: Be very careful with commands that include --hard. They can permanently delete your work! When in doubt, make a backup copy of your project folder first. I learned this the hard way.

Sharing your work with the world

This is where things get really exciting! GitHub is like Google Drive for code - it stores your projects online and makes them easy to share. Here's how to get your local Git repository onto GitHub:

  1. Create a GitHub account - Go to github.com and sign up. It's free for public repositories.
  2. Create a new repository - Click the "+" button in the top right and select "New repository"
  3. Give it a name - I usually use the same name as my local project folder to keep things simple
  4. Connect your local repo to GitHub - Copy the repository URL from GitHub and run these commands:
Connect to GitHub
git remote add origin https://github.com/yourusername/your-repo-name.git
git branch -M main
git push -u origin main

That's it! Your code is now backed up online and you can share the GitHub URL with anyone.

Understanding the commands:
  • remote add origin tells Git where your online repository is
  • branch -M main renames your main branch (some older tutorials use "master")
  • push -u origin main uploads your commits to GitHub

Working with others (or just keeping things synced)

Once your code is on GitHub, you'll need these commands to stay in sync:

Download latest changes
git pull origin main
Upload your changes
git push origin main
Good habit: Always pull before you push. This grabs any changes that might have happened since you last synced and helps avoid conflicts.

Things I learned the hard way

My biggest Git mistakes (so you don't repeat them)
  • Committing huge files: I once committed a 500MB video file. GitHub wasn't happy. Use .gitignore files!
  • Terrible commit messages: "fixed stuff" tells you nothing. Be specific!
  • Not committing often enough: I used to work for days without committing. Then I'd lose work. Commit early, commit often!
  • Fear of breaking things: Git is designed to help you recover from mistakes. Don't be afraid to experiment!

Write better commit messages

Good commit messages are like breadcrumbs for your future self. Here's what I've learned works well:

❌ Vague messages
  • "fixed bug"
  • "updated stuff"
  • "changes"
  • "idk"
✅ Clear, specific messages
  • "Fix login form validation on signup page"
  • "Add responsive design for mobile navigation"
  • "Update API endpoint for user profiles"
  • "Remove unused CSS from homepage"

Use .gitignore files

Create a file called .gitignore in your project root to tell Git which files to ignore. Here's a basic one I use for web projects:

Sample .gitignore file
# Dependencies
node_modules/
vendor/

# Environment files
.env
.env.local

# System files
.DS_Store
Thumbs.db

# Logs
*.log

Commit frequently

I used to think I needed to finish entire features before committing. Wrong! Commit whenever you've made a logical chunk of progress. It's like saving your document while writing - you wouldn't wait until the entire essay is done, right?

What's next in your Git journey?

You now know enough Git to start using it in your projects! But there's so much more to explore:

  • Branching: Create separate "branches" to experiment with new features
  • Merging: Combine changes from different branches
  • Pull requests: Propose changes to other people's projects
  • Git workflows: Team strategies for managing code
  • Advanced commands: Rebasing, cherry-picking, and more
My advice: Don't try to learn everything at once. Start using basic Git for your projects, and gradually add new concepts as you need them. The best way to learn Git is by using it regularly, even for small personal projects.
Final thoughts
Git felt overwhelming when I started, but now I can't imagine coding without it. It's saved my bacon countless times and made collaboration so much easier. Start small, be patient with yourself, and don't be afraid to make mistakes - Git is there to help you recover from them. You've got this!
