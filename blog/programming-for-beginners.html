01 — Foundation

What is programming?

Programming is expressing human intent as precise, unambiguous instructions a machine can execute reliably, every time. It is as much about thinking as it is about typing.

~5 min
📋
Analogy

Think of a recipe. It produces the same dish every time regardless of who follows it. A program is exactly that — except the cook is a machine that is perfectly literal, never improvises, and works at billions of steps per second.

The word "computer" originally described a person who computed things by hand. Machines took over — but the word stuck. Programming is directing those machines.

Most beginners assume the hard part is memorising syntax. It is not. The hard part is learning to think precisely — leaving no ambiguity, no implicit assumption. Syntax is easy; you look it up.

01a

Problem solving

Programming begins with a problem. The craft is translating a fuzzy human need into something a machine can execute exactly.

01b

Decomposition

Large problems become manageable when broken into small, independent pieces. One of the most durable mental habits programming builds.

01c

Precision

Computers do exactly what they are told — not what you meant. Ambiguity is the root cause of nearly every bug you will encounter.

01d

Abstraction

Good programmers hide complexity behind simple interfaces. You call a function without knowing how it works inside — that is abstraction.

02 — Hardware

How computers think

Computers do not think — they switch. Understanding this removes the mystery from programming and explains why precision matters so much.

~5 min

At the lowest level, a computer's entire operation is identical to a light switch: on or off, 1 or 0. That is binary. Stack a billion switches, cycle them billions of times per second, and you get a modern processor.

This is not intelligence — it is speed. Computers cannot reason, improvise, or fill gaps. But they execute simple rules faster than any human, making them extraordinarily powerful when given precise instructions.

Memory comes in layers: Registers (fastest, a few bytes), RAM (fast, temporary — clears on shutdown), Storage (slow, permanent). Programs live in RAM while running and storage when at rest.

Binary

1s and 0s

Every number, letter, image, and sound is a sequence of 1s and 0s. All other representations are conventions layered on top.

Speed

Billions/second

A modern CPU runs at 3–5 GHz. Not clever — fast. Speed at scale produces the appearance of intelligence.

RAM

Working memory

RAM holds what a program is actively using. Lose power, lose contents. Why unsaved work vanishes in a crash.

CPU cycle

Fetch → decode → execute

That four-step loop, running billions of times per second, is all a CPU actually does.

03 — Logic

Algorithms

A finite, ordered sequence of unambiguous steps that transforms an input into an output. You use dozens of algorithms every day without realising it.

~5 min

"Algorithm" sounds academic but the concept is mundane: a recipe, assembly guide, morning routine. What makes it a proper algorithm is that each step is finite, ordered, and unambiguous.

A good algorithm is correct for all valid inputs — not just the easy ones. "Sort the list" is a goal. A sorting algorithm describes exactly how to move items. Dozens of sorting algorithms exist, each with different speed and memory trade-offs.

Write your algorithm in plain English before writing any code. If it is unclear in English, it will be wrong in code.

Input

What goes in

Every algorithm operates on defined inputs. Specifying them precisely is often the hardest part.

Process

The steps

"Compare adjacent elements and swap if out of order" is a step. "Sort the list" is a goal. Each step must be executable without ambiguity.

Output

What comes out

Same input → same output, every time. Predictability is the defining quality of a correct algorithm.

Efficiency

Time & space

Two algorithms can solve the same problem at very different speeds. Big O notation describes how performance scales with input size.

05 — Core concepts

Four building blocks

These four patterns appear in virtually every program ever written. Understand them and the rest of programming becomes variations on a theme.

~8 min

A variable is a name bound to a value stored in memory. You can read it, update it, and pass it around. Like a labeled box — the label is the name, the contents can change.

Variables have scope: where in a program they are visible. A variable inside a function usually cannot be seen outside it. Understanding scope prevents entire categories of bugs.

Variables also have types, even if the language infers them (Python) rather than requiring explicit declaration (Java).

Python — variables
name = "Alice" # string age = 29 # integer height = 1.72 # float active = True # boolean age = age + 1 # now 30 name = name.upper() # "ALICE" x, y, z = 1, 2, 3 # multiple assignment

A function is a named, reusable block of code. Define it once, call it as many times as you need. Without functions you would copy the same logic everywhere — and fix bugs in every copy.

Functions take parameters (inputs) and optionally return a value (output). This is the primary tool for keeping code DRY — Do not Repeat Yourself.

A well-named function documents itself. Code that reads calculateTax(income) needs no comment.

Python — functions
def greet(name, formal=False): if formal: return "Good day, " + name + "." return "Hey, " + name + "!" print(greet("Alice")) # Hey, Alice! print(greet("Bob", formal=True)) # Good day, Bob.

A loop executes a block of code repeatedly. Without loops, processing 1,000 items means writing 1,000 lines. With a loop, four lines regardless of count.

for loops iterate over a known collection. while loops repeat as long as a condition is true. The danger with while loops is accidentally writing an infinite loop — one that never stops.

Loops can be nested. A 1,000-item loop inside another 1,000-item loop runs one million iterations — be careful.

Python — loops
# For loop — iterate a collection fruits = ["apple", "banana", "cherry"] for fruit in fruits: print(fruit.upper()) # While loop — condition-based count = 0 while count < 5: print("Step", count) count += 1 # must progress toward exit!

A condition lets the program take different paths based on data. Without conditions, every run produces the same result regardless of input.

The core type is if / elif / else. Conditions evaluate to boolean (True/False). Comparison operators (>, ==, !=) return booleans. Logical operators (and, or, not) combine them.

A very common mistake: using a single = (assignment) instead of == (comparison) inside a condition.

Python — conditions
temp = 28 if temp > 30: print("Hot") elif temp > 20: print("Warm") # this runs else: print("Cool") if temp > 20 and temp < 30: print("Perfect") # True

06 — Data

Types of data

Every value in a program has a type. Types determine what operations are valid and how data is stored in memory.

~6 min
Integer

Whole numbers

0, 1, -3, 1000. Counting, indices, ages. No decimal point. Math is exact.

Float

Decimal numbers

3.14, -0.5. Note: floats have rounding errors. 0.1 + 0.2 does not equal 0.3 in most languages.

String

Text

"hello", "42", "user@mail.com". Always quoted. "42" and 42 are completely different types.

Boolean

True / False

Exactly two values. Every comparison returns a boolean. Essential for all conditions.

None / Null

Absence of value

Represents "nothing" or "not yet set". Forgetting to handle None is a very common source of crashes.

List / Array

Ordered collection

[1, 2, 3]. Items accessed by index starting at 0. Can hold any type, even mixed.

Dictionary

Key-value pairs

{"name":"Alice","age":30}. Look up by key, not position. Fast and very flexible.

Tuple

Immutable list

(1, 2, 3). Like a list but cannot be changed. Good for data that must stay fixed.

Set

Unique values

{1, 2, 3}. No duplicates. Useful for membership tests and de-duplication.

⚠️
Type errors are very common

Trying to add a string to a number ("5" + 2) crashes in most languages. Data from files, APIs, and user input almost always arrives as a string and needs converting before use.

07 — OOP New

Object-oriented programming

OOP structures code around objects — bundles of data and the functions that operate on them. Most modern codebases use it. You will encounter it constantly.

~7 min

Imagine modelling a bank account. You need to store a balance and support deposit and withdraw operations. OOP lets you bundle those together into a single class.

A class is a blueprint. An object (or instance) is what you actually use — like a cookie cutter (class) and the cookies it makes (objects). Thousands of BankAccount objects from one BankAccount class.

The four core OOP concepts: Encapsulation (keep data and behavior together), Inheritance (one class extends another), Polymorphism (different objects, same interface), Abstraction (hide complexity behind simple methods).

You do not need to master OOP to start programming — but you will encounter it immediately when reading real code.

Python — class example
class BankAccount: def __init__(self, owner, balance=0): self.owner = owner self.balance = balance def deposit(self, amount): self.balance += amount print("Deposited", amount) def withdraw(self, amount): if amount > self.balance: print("Insufficient funds") else: self.balance -= amount acc = BankAccount("Alice", 1000) acc.deposit(500) # balance → 1500 acc.withdraw(200) # balance → 1300
Encapsulation

Bundle data + behavior

Keep data and the code that operates on it in the same place. Prevents other parts of the program from accidentally corrupting it.

Inheritance

Extend a class

A SavingsAccount can inherit from BankAccount and add interest logic without rewriting everything. Code reuse at the structural level.

Polymorphism

Same interface, different behavior

A draw() method on Circle and Square can both be called the same way, but each behaves differently internally.

08 — Method

How programmers solve problems

Writing code is the last step, not the first. Experienced programmers spend more time thinking than typing — and their programs reflect it.

~6 min
Step 01

Understand

Can you explain it to someone else in plain language? If not, you do not understand it well enough to code it.

Step 02

Decompose

Break into the smallest possible independent sub-problems. Solve each one, then combine.

Step 03

Plan in English

Write numbered steps before touching the keyboard. If it is unclear in English, it will be wrong in code.

Step 04

Simplest version first

Make it correct before making it fast or elegant. A slow correct solution beats a fast wrong one every time.

Step 05

Test thoroughly

Try expected inputs, then edge cases: empty, negatives, maximums, wrong types. Bugs live in corners.

Step 06

Refactor

Once working and tested, improve clarity and efficiency. Never refactor broken code — fix first, clean second.

09 — Debugging New

Finding and fixing bugs

Debugging is not a sign of failure — it is the normal state of programming. Getting good at it is as important as writing code.

~7 min

Bugs come in three varieties: Syntax errors (grammatically wrong — the program will not run), runtime errors (the program crashes while running), and logic errors (runs but produces wrong results — the hardest to find).

Rule one: read the error message. It tells you what went wrong and usually where. Most beginners panic and ignore it. Do not.

Rule two: change one thing at a time. If you change three things and the bug disappears, you do not know what fixed it — or whether it is truly fixed.

Stack traces: when a program crashes, it prints the chain of function calls that led there. Read it bottom-up — the actual error is usually at the bottom.

Print debugging is the most accessible technique: insert print() statements to see what values variables hold at each point. Simple, always available, works everywhere. Remove them when done.

Every serious editor has a debugger: pause the program at any line, inspect all variable values, and step through execution one line at a time. Learning to use it is one of the highest-leverage skills you can develop early.

Rubber duck debugging: explain your code out loud to an inanimate object, line by line. The act of explaining forces precision, and you will often spot the bug mid-sentence. It sounds absurd. It works.

Technique 01

Print debugging

Insert print statements to trace variable values. Simple, always available, works everywhere.

Technique 02

Breakpoints

Pause at a specific line and inspect everything. Available in VS Code, PyCharm, browser DevTools. Far more powerful than print once you learn it.

Technique 03

Rubber duck

Explain your code out loud, line by line, to anything. You will hear your own incorrect assumptions.

Technique 04

Binary search

Comment out half your code. Does the bug still occur? No means bug is in commented half. Repeat until isolated.

Technique 05

Stack traces

Read bottom-up. The actual error is usually at the bottom. The top shows how you got there.

Technique 06

Fresh eyes

If stuck for 30+ minutes, take a break. Return fresh. The solution almost always appears within minutes.

10 — Habits New

Comments, docs & clean code

Code is read far more often than it is written. The programmer who will read your code most is you, six months from now, having completely forgotten what you were thinking.

~6 min

A comment is a line ignored by the computer but read by humans. Use comments to explain why a decision was made, not what the code does — that should be clear from the code itself.

Documentation is comments at the function or module level describing what something does, what it expects, and what it returns. Python uses docstrings; Java uses Javadoc.

✓
Good comment

# Retry 3x — this API returns 503 intermittently on deploy
Explains why, not what. No redundancy with the code.

✗
Redundant comment

# Add 1 to count    count = count + 1
Restates the obvious. Adds noise, no value whatsoever.

Python — docstrings and naming
def calculate_discount(price, pct): """ Apply a percentage discount to a price. Args: price (float): Original price in GBP pct (int): Discount percentage, 0-100 Returns: float: Discounted price, rounded to 2dp Raises: ValueError: if pct not between 0 and 100 """ if not (0 <= pct <= 100): raise ValueError("pct must be 0-100") return round(price * (1 - pct / 100), 2)
Naming

Names matter enormously

d vs discount_percentage. The second takes a second longer to type and saves minutes every time anyone reads it. Always use descriptive names.

DRY

Do not repeat yourself

If you wrote the same logic twice, it will eventually be in two different states. Extract it into a function — one source of truth.

KISS

Keep it simple

The simplest solution that works is usually the best. Cleverness in code is a liability; clarity is an asset.

11 — Git New

Version control & Git

Git lets you track every change, undo mistakes, and collaborate without overwriting each other's work. Every professional programmer uses it. Start from day one.

~7 min

Think of Git as an infinite undo history that works at the project level. Every commit is a snapshot of your entire project. You can return to any snapshot at any time.

Branching: create a separate copy of your code to experiment on, then merge the changes back when ready — without touching the working version. If the experiment fails, discard the branch; nothing is lost.

GitHub (and GitLab, Bitbucket) is an online host for Git repositories. Your code lives on their servers as a backup, and it is where the open-source community lives — you can view and contribute to millions of real projects.

Three concepts explain 80% of Git usage: commit (save a snapshot), push (upload to GitHub), pull (download changes). Everything else builds on these.

Git — essential commands
# Start tracking a project git init # Stage changes git add . # everything git add script.py # one file # Commit with a message git commit -m "Add login validation" # Upload to GitHub git push origin main # Download latest changes git pull # See what changed git status git log --oneline
Commit

Save a snapshot

Records what changed, when, and why. Good messages read like a changelog: "Fix null pointer in login handler."

Branch

Parallel development

Work on a feature in isolation. Merge when done. If it fails, discard — nothing on main is affected.

Pull request

Code review

On GitHub, propose merging a branch. Others review, comment, approve before it goes in. Standard practice on every team.

💡
Start immediately

Create a GitHub account and commit your practice code from day one. Your commit history is evidence of your learning journey — and eventually part of your portfolio. Employers look at GitHub profiles.

12 — Web & APIs New

How the web works & APIs

Most software today is connected. Understanding how programs talk to each other unlocks an enormous range of things you can build.

~7 min

When you type a URL, your computer sends an HTTP request to a server. The server processes it and sends back a response — usually HTML, JSON, or an image.

HTTP has four main methods: GET (retrieve data), POST (send new data), PUT (update existing data), DELETE (remove data). These four cover almost everything.

An API (Application Programming Interface) is a defined way for programs to talk to each other. Your weather app calls a weather API. Login with Google is an API call. Most useful internet programs expose an API.

JSON is the most common format APIs use to exchange data. It looks exactly like a Python dictionary and every language can parse it easily.

Python — calling a real API
import requests url = "https://api.github.com/users/torvalds" response = requests.get(url) print(response.status_code) # 200 = success data = response.json() print(data["name"]) # Linus Torvalds print(data["public_repos"]) # number of repos
HTTP 200

OK

Request succeeded. You got what you asked for.

HTTP 404

Not found

The resource does not exist at that URL.

HTTP 401

Unauthorized

You need to authenticate first — API key, token, or login.

HTTP 500

Server error

Something went wrong on the server's side. Usually not your fault.

JSON

Universal data format

{"key": "value"} — identical to a Python dict. Every language can parse it. The lingua franca of APIs.

REST

API design style

A convention for structuring APIs using HTTP methods. GitHub, Stripe, Twitter — most public APIs are REST.

13 — Pitfalls

Common beginner mistakes

Everyone makes these. Knowing them in advance does not make you immune — but you will recognise them faster and recover quicker.

~5 min
01

Coding before thinking

Jumping straight to the editor. Result: code that solves a slightly different problem than the one you meant to solve.

02

Ignoring error messages

Error messages tell you what went wrong and usually where. Read every word before changing anything.

03

Over-engineering early

Building a complex solution before a simple one works. Get it working first, then improve.

04

Insufficient testing

Only testing the happy path. Real bugs live in edge cases: empty inputs, negatives, very large values.

05

Tutorial purgatory

Watching tutorials indefinitely without building anything. Understanding is not ability. You learn to code by coding.

06

Copy-pasting blindly

Taking code from Stack Overflow without reading it. Paste it, yes — but understand every line before moving on.

07

Comparing your progress

Measuring yourself against people at a different stage. The only useful comparison is yourself six months ago.

08

Quitting at friction

Confusion is not a signal to stop — it is a signal that learning is happening. The discomfort is your mental model changing.

09

Never committing to Git

Working for days without commits. One bad edit and you lose everything. Commit early, commit often.
