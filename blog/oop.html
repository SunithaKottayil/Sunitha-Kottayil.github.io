Object-Oriented Programming (OOP)

A complete technical breakdown of OOP pillars and architectural concepts using the school classroom model.

1. What is Object-Oriented Programming?

Object-Oriented Programming (OOP) is an architectural paradigm that organizes software design around data structures called objects, rather than functions and sequential logic alone. Each object binds two things together:

  • State (Attributes / Data): What the object knows or stores (e.g., a student's name, enrolled grade, or test score).
  • Behavior (Methods / Operations): What the object can do or compute (e.g., studying, taking a test, or submitting assignments).

In procedural programming, data and functions live separately—functions accept raw data, mutate it, and pass it around. In OOP, data and the operations that mutate it are packaged into a single cohesive boundary.

2. The Four Pillars of OOP

I. Classes and Objects

A Class is a blueprint or programmer-defined type. It defines the names of fields and methods that every instance will have. An Object is a physical instance allocated in memory with concrete values assigned to those fields.

Technical Mechanics:

  • __init__: The constructor method automatically executed by the runtime whenever a new instance is instantiated.
  • self: A reference to the current instance being operated on, ensuring operations modify the correct object's memory space.
class Student:
    # Class variable (shared by all instances)
    school_name = "Westfield Academy"

    def __init__(self, name, student_id, grade):
        # Instance variables (unique to each object instance)
        self.name = name
        self.student_id = student_id
        self.grade = grade
        self.gpa = 0.0

    # Instance method operating on instance state
    def study(self, subject, hours):
        return f"{self.name} studied {subject} for {hours} hours."

    def record_gpa(self, new_gpa):
        self.gpa = new_gpa

# Instantiating concrete objects from the Student class:
student_1 = Student("Alice Hansen", 101, 10)
student_2 = Student("Bob Jensen", 102, 11)

# Both share the same method definitions, but mutate separate state:
student_1.record_gpa(3.8)
student_2.record_gpa(3.2)

print(student_1.study("Chemistry", 2))  # Alice Hansen studied Chemistry for 2 hours.
Key Distinction: Student is a data type (stored once in code memory). student_1 and student_2 each occupy distinct memory addresses with their own independent instance variables.

II. Encapsulation

Encapsulation is the mechanism of restricting direct access to some of an object's components and bundling data with the methods that operate on that data. It prevents the internal state of an object from being left in an invalid or corrupt state.

Why Encapsulation Matters:

  • Invariant Protection: Enforces business logic (e.g., a student's age cannot be set to negative or impossible values).
  • Implementation Hiding: Internal storage structures can change without breaking callers using public interfaces.
class EnrolledStudent:
    def __init__(self, name, age):
        self.name = name
        # Leading underscore denotes private/protected attribute by convention
        self._age = age
        self._attendance_days = 0

    # Controlled Getter
    @property
    def age(self):
        return self._age

    # Controlled Setter with validation boundary
    @age.setter
    def age(self, value):
        if not isinstance(value, int) or value < 5 or value > 100:
            raise ValueError("Invalid student age. Must be an integer between 5 and 100.")
        self._age = value

    # Methods modify internal counters safely
    def mark_attendance(self):
        self._attendance_days += 1

    def get_attendance_record(self):
        return self._attendance_days

student = EnrolledStudent("Clara", 15)
student.age = 16        # Allowed: passes through setter validation
# student.age = -5      # Throws ValueError: prevents invalid state
Rule of Thumb: Never expose raw internal variables directly if invalid values could break application integrity. Protect them using getters/setters or properties.

III. Inheritance

Inheritance allows a new class (derived/child class) to inherit attributes and methods from an existing class (base/parent class). It enables code reuse and establishes an "is-a" taxonomic relationship.

Technical Mechanics:

  • Base Class: The generalized parent entity that implements shared foundational logic.
  • Derived Class: The specialized child entity that automatically receives base methods and can add unique behaviors.
  • super(): Calls the parent class constructor and methods, preventing duplicate initialization code.
# General Base Class
class Student:
    def __init__(self, name, student_id):
        self.name = name
        self.student_id = student_id

    def check_in(self):
        return f"Student {self.name} checked into school grounds."

# Specialized Child Class (ScienceStudent IS A Student)
class ScienceStudent(Student):
    def __init__(self, name, student_id, lab_bench_number):
        # Delegate base field assignment to parent
        super().__init__(name, student_id)
        self.lab_bench_number = lab_bench_number

    # Unique behavior specific only to ScienceStudent
    def perform_titration(self):
        return f"{self.name} is running an acid-base experiment at Bench {self.lab_bench_number}."

sci_student = ScienceStudent("David", 201, 4)
print(sci_student.check_in())           # Inherited from Student parent
print(sci_student.perform_titration())  # Defined in ScienceStudent child

IV. Polymorphism

Polymorphism means "many forms." It allows different object types to respond to the same method call in their own specialized way. The caller does not need to know the specific concrete class type at runtime—only that it implements the common interface.

Technical Mechanics:

  • Method Overriding: A child class provides a custom implementation of a method that is already defined in its parent class.
  • Unified Dispatch: A client loop or service can iterate over mixed collection types and invoke the same method signature on all of them without type branching (if/else checks).
class Student:
    def __init__(self, name):
        self.name = name

    def take_assessment(self):
        raise NotImplementedError("Subclasses must implement take_assessment")

class MathStudent(Student):
    def take_assessment(self):
        return f"{self.name} is solving 25 calculus integrals under timed conditions."

class ArtStudent(Student):
    def take_assessment(self):
        return f"{self.name} is presenting a portfolio of acrylic landscape studies."

class DramaStudent(Student):
    def take_assessment(self):
        return f"{self.name} is performing a Shakespearean soliloquy in the auditorium."

# Polymorphic Execution: The caller treats all items identically as 'Student'
exam_hall = [
    MathStudent("Marcus"),
    ArtStudent("Elena"),
    DramaStudent("Lucas")
]

for student in exam_hall:
    # Single uniform method call, distinct runtime execution:
    print(student.take_assessment())
Design Benefit: Adding a MusicStudent class requires zero changes to the evaluation loop. The loop calls student.take_assessment(), maintaining open/closed architectural design.

3. Supporting OOP Concepts: Abstraction & Composition

Complete mastery of OOP requires understanding two companion architectural principles that accompany the four primary pillars:

Concept Relationship Type Core Purpose
Inheritance "Is-A" (e.g., ScienceStudent is a Student) Hierarchical specialization and foundational code reuse.
Composition "Has-A" (e.g., Classroom has a Student roster) Combining independent decoupled objects into higher-level systems.
Abstraction Interface Contract Hiding internal complexity while exposing only necessary operational controls. 
class Locker:
    def __init__(self, number):
        self.number = number

# Composition: Student HAS A Locker (loose coupling)
class ResidentStudent:
    def __init__(self, name, locker_num):
        self.name = name
        self.locker = Locker(locker_num)  # Composed object instance
